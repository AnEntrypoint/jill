Typed decisions, answered by Haiku subagents

jill

jill answers small typed questions about a piece of text, using a claude-haiku-5-5 subagent in place of TypeSafe’s Jev, a cloud decision model.

In a terminal:

npx skills add AnEntrypoint/jill

Paste into your agent:

Use jill: which lane should this message go in, and does a person need to see it now?

Needs Node.js and an agent with an Agent tool.

How it works

  1. Step 1: Prepare chunks

    Group the questions that share one state (the text the questions are about) into chunks of up to eight. The state is copied into each chunk: ten questions make one chunk of eight and one of two.

  2. Step 2: Dispatch Haiku subagents in parallel

    Send one subagent per chunk on claude-haiku-5-5 (model: "haiku"), all in one message. Each runs at low effort, read-only, as the jill-decider agent when the plugin lists it, otherwise as Explore.

  3. Step 3: Merge

    Each reply has one line per question, in the form id|value|confidence, not JSON. Merge the replies into one answer per question, and check each one against the list below.

Checks on the answers

  • Every question has exactly one answer: a real option for a choice, a value inside the scale for a score.
  • A noul answer (a yes or no statement about the state, the third type below) comes back as yes or no, which becomes true or false.
  • Anything invalid is flagged, never guessed.
  • Below 0.6 confidence, ask that question again once on the sonnet model at low effort (the timing is under Speed), or route it to a person.

Three question types

Each question has one of three types.

Choice

Pick one option.

{
  "id": "lane",
  "type": "choice",
  "question": "Which lane?",
  "options": [
    "billing",
    "shipping",
    "support",
    "spam"
  ]
}

Score

Place the state (the text being judged) on a scale. The ends are the question’s own, for example 0 for not urgent and 1 for most urgent.

{
  "id": "urgency",
  "type": "score",
  "question": "How urgent?",
  "scale": [0, 1]
}

Noul (yes or no)

Is a yes or no statement true of the state? Unlike choice and score, it has no options or scale.

{
  "id": "refund",
  "type": "noul",
  "question": "Asks for a refund."
}

The example below answers the lane question for this state: “I was charged twice for order 1043. Can I have one charge back?”

Example reply

lane: billing, confidence 0.97

One answer, with the three fields the skill returns for each question: id, value and confidence. Every answer carries its own confidence from 0 to 1. Below 0.6, the state did not settle the question, so ask it again on sonnet (see Merge) or route it to a person. This one is an example, not a measured result.

A failed answer

{
  "id": "lane",
  "value": null,
  "confidence": 0,
  "error": "not_an_option"
}

An answer that is missing or invalid comes back unknown, with an error field. The caller never guesses. If a chunk’s reply fails to parse, the skill re-dispatches that chunk once; if it still fails, those answers stay unknown and the caller takes its default path.

Fifteen ready-made question sets

Question sets for common decisions, in references/policies.md, ready to paste as a question list. The file has fifteen; they are listed here. To write your own, give each question an id and pick one type: choice, score or noul.

  • Model routing: the cheapest model tier good enough for a turn. Risky work never goes to the cheapest tier.
  • Skill selection: which installed skill a turn needs, or none.
  • Triage: what kind of message it is, how urgent, and whether a person must see it now.
  • Mailbox lanes: which lane a message belongs in, and whether it deserves attention.
  • Memory filter: which retrieved passages help answer the current question, and which carry instructions aimed at an agent.
  • Turn selection: which turns to keep when a transcript has to be cut.
  • Injection screen: whether web or tool output tries to instruct an agent.
  • Command gate: whether a shell command is safe to run without review.
  • Pull request risk: how risky a change is, and whether a senior engineer must review it.
  • Incident severity: how bad an incident is, and whether on-call must be paged now.
  • Personal data: whether a text holds personal or sensitive information, and whether it can be shared.
  • Search result selection: which results are worth opening, and which are probably out of date.
  • Evidence sufficiency: whether the evidence answers the question without more searches, how directly it supports the answer, and whether two pieces contradict each other.
  • Next browser action: which page action moves the goal forward, and whether it can be undone or sends personal or payment data.
  • Handoff worthiness: which turns record a decision or a constraint that a later session must keep.

Worked example: triage

[
  {
    "id": "kind",
    "type": "choice",
    "question": "What kind is it?",
    "options": [
      "bug",
      "question",
      "request",
      "billing",
      "other"
    ]
  },
  {
    "id": "urgency",
    "type": "score",
    "question": "How urgent is it?",
    "scale": [0, 1]
  },
  {
    "id": "human",
    "type": "noul",
    "question": "Needs a person now."
  }
]

Same ids, types and options as policies.md. Two question texts are reworded so each line fits a phone’s width; the exact wording is in that file. The caller maps the answers to actions itself.
