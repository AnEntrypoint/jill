Typed decisions, answered by Haiku subagents

jill

jill answers small typed questions about a piece of text, using a claude-haiku-5-5 subagent in place of TypeSafe’s Jev, a cloud decision model.

The npx route needs Node.js. Either route needs an agent with an Agent tool.

In a terminal:

npx skills add AnEntrypoint/jill

Or in Claude Code:

/plugin marketplace add AnEntrypoint/jill
/plugin install jill@jill

Then ask your agent:

Use jill: which lane should this message go in, and does a person need to see it now?

An illustrative reply, not a measured result:

lane|billing|0.97

One line per question: id|value|confidence. The state is in step 3, under How it works; the lane question is under Three question types.

How it works

  1. Step 1: Prepare chunks

    Group the questions that share one state (the text the questions are about) into chunks of up to eight. The state is copied into each chunk: ten questions make one chunk of eight and one of two. Token mode in Speed, and the dense protocol (the items sit in a file, each subagent reads its own range and replies with one short code line per item) for hundreds of items, are the exceptions. Token mode sends 9 to 16 questions as one chunk.

  2. Step 2: Dispatch Haiku subagents in parallel

    Send one subagent per chunk on claude-haiku-5-5 (model: "haiku"), all in one message, at low effort and read-only. Use the jill-decider agent, the single-tool agent the plugin ships, if the plugin lists it; otherwise use Explore, a search subagent type.

  3. Step 3: Merge

    Each reply has one line per question, in the form id|value|confidence, not JSON. Merge the replies into one answer per question, and check each one against the list below.

    The state is the message the prompt asks about: “I was charged twice for order 1043. Can I have one charge back?”

    An illustrative reply to the noul question (a yes-or-no question) “does a person need to see it now”, the last question in the example prompt at the top of the page, not a measured one. The merge turns yes into true:

    human|yes|0.91

Checks on the answers

  • Every question has exactly one answer: a real option for a choice, a value inside the scale for a score.
  • A noul answer (a yes or no statement about the state, the third type below) comes back as yes or no, which becomes true or false.
  • Anything invalid is flagged, never guessed.
  • Below 0.6 confidence, you can ask that question again once on the sonnet model at low effort (the timing is under Speed), or route it to a person. Ask again only where the caller needs a firmer answer.

Three question types

Each question has one of three types.

Choice

Pick one option.

{
  "id": "lane",
  "type": "choice",
  "question": "Which lane?",
  "options": [
    "billing",
    "shipping",
    "support",
    "spam"
  ]
}

Score

Place the state (the text being judged) on a scale. The ends are the question’s own, for example 0 for not urgent and 1 for most urgent.

{
  "id": "urgency",
  "type": "score",
  "question": "How urgent?",
  "scale": [0, 1]
}

Noul (yes or no)

Is a yes or no statement true of the state? Unlike choice and score, it has no options or scale.

{
  "id": "refund",
  "type": "noul",
  "question": "Asks for a refund."
}

The example below answers the lane question for the state in step 3 of How it works.

Example reply

lane: support, confidence 0.52. Below 0.6, this is the answer the Checks list would ask again on sonnet or route to a person.

One answer, with the three fields the skill returns for each question: id, value and confidence. Every answer carries its own confidence from 0 to 1. This one is an example, not a measured result.

A failed answer

{
  "id": "lane",
  "value": null,
  "confidence": 0,
  "error": "not_an_option"
}

An answer that is missing or invalid comes back unknown, with an error field. The caller never guesses. If a chunk’s reply fails to parse, the skill re-dispatches that chunk once; if it still fails, those answers stay unknown and the caller takes its default path.

Fifteen ready-made
question sets

Question sets for common decisions, in references/policies.md, ready to paste as a question list. The file has fifteen; they are listed here, with the types each set uses in brackets. To write your own, give each question an id and pick one type: choice, score or noul (a yes or no statement).

  • Model routing (choice, noul): the cheapest model tier good enough for a turn. Risky work never goes to the cheapest tier.
  • Skill selection (choice, score): which installed skill a turn needs, or none.
  • Triage (choice, score, noul): what kind of message it is, how urgent, and whether a person must see it now.
  • Mailbox lanes (choice, noul): which lane a message belongs in, and whether it deserves attention.
  • Memory filter (noul): which retrieved passages help answer the current question, and which carry instructions aimed at an agent.
  • Turn selection (noul, score): which turns to keep when a transcript has to be cut.
  • Injection screen (noul, score): whether web or tool output tries to instruct an agent.
  • Command gate (noul, choice): whether a shell command is safe to run without review.
  • Pull request risk (choice, noul): how risky a change is, and whether a senior engineer must review it.
  • Incident severity (choice, score, noul): how bad an incident is, and whether on-call must be paged now.
  • Personal data (noul, choice): whether a text holds personal or sensitive information, and whether it can be shared.
  • Search result selection (noul, score): which results are worth opening, and which are probably out of date.
  • Evidence sufficiency (noul, choice): whether the evidence answers the question without more searches, how directly it supports the answer, and whether two pieces contradict each other.
  • Next browser action (choice, noul): which page action moves the goal forward, and whether it can be undone or sends personal or payment data.
  • Handoff worthiness (noul, score): which turns record a decision or a constraint that a later session must keep.

Speed

In jill’s speed mode, 16 questions go out as two parallel 8-question calls. They take about 3.4 to 4.1 s and about 33k subagent tokens. Both are derived from the 8-question runs below, not measured as one 16-question run.

Token mode is one exception to Step 1’s limit of eight. The caller chooses it when the wall clock does not matter and the question count is 9 to 16. All of them go in one call instead of two, at 6.5 s and 17.6k subagent tokens (README, Speed section, line 69). For hundreds to thousands of items, the dense protocol is the other exception (README, Speed section, lines 62 to 65).

Measured on the Agent path, as the project README records them. Effort is the effort setting passed with each Agent-tool call: jill sets it to low, and default effort is the setting it is compared with.

The two-call gain (2.8 s against 3.4 s) is not firm.

Re-asking two uncertain answers on sonnet at low effort took 2.4 s, one sample.

Plan, one sample: 4.3 s and 16.7k subagent tokens. The README does not state Plan’s effort or set size, so it is not set against the 8-question Explore runs above. The README does not say what the subagent token counts include.

Identical decisions on the same state are reused within a conversation, so repeats cost no model call.
